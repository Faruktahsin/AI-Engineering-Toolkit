# ADR-001: Identifier Strategy, Namespaces, & Import/Export Guarantees

* **Status:** Accepted
* **Date:** 5 August 2026
* **Deciders:** Senior Software Architect
* **Technical Domain:** Data Persistence & System Interoperability

## Context & Problem Statement
The refactored domain model requires identifiers (`entity_id`, `directive_id`, `assertion_id`, `event_id`, `relation_id`) across all 5 primitives. Without a standardized identifier format, namespacing rule, and import/export collision policy, independent implementations will generate incompatible primary keys, breaking foreign-key validation in `RELATION` edges.

## Decision Drivers
* **10-Year Durability**: Identifiers must remain sortable, collision-free, and stable across systems.
* **Human-Readable Namespacing**: IDs must convey their underlying primitive class during debugging.
* **Deterministic Parsing**: IDs must be parseable without database lookup.

## Decision Outcome

### 1. Identifier Format
All identifiers across PAKB MUST use **Prefixed Crockford Base32 ULIDs** (Universally Unique Lexicographically Sortable Identifiers).
* **Structure:** `<prefix>_<26-character-ulid>`
* **Regex Standard:** `^(ent|dir|ast|evt|rel)_[0-9A-HJKMNP-TV-Z]{26}$` (Case-insensitive Crockford Base32).

### 2. Primitive Namespace Prefixes

| Primitive Class | Prefix | Example Identifier |
|---|---|---|
| **`ENTITY`** | `ent_` | `ent_01J4X89K9Z1A2B3C4D5E6F7G8H` |
| **`DIRECTIVE`** | `dir_` | `dir_01J4X89K9Z2B3C4D5E6F7G8H9I` |
| **`ASSERTION`** | `ast_` | `ast_01J4X89K9Z3C4D5E6F7G8H9I0J` |
| **`EVENT`** | `evt_` | `evt_01J4X89K9Z4D5E6F7G8H9I0J1K` |
| **`RELATION`** | `rel_` | `rel_01J4X89K9Z5E6F7G8H9I0J1K2L` |

### 3. Stability & Import/Export Guarantees
* **Immutability:** An ID is generated once at primitive creation and MUST NEVER be altered or reassigned.
* **Import Collision Resolution:**
  * If an incoming primitive matches an existing ID **and** has identical content (matching SHA-256 hash), the import operation is idempotent (no-op).
  * If an incoming primitive matches an existing ID but has differing content, the import MUST throw `IDCollisionError` unless executed with `--autorename`.
  * When `--autorename` is specified, a new ULID is generated for the incoming primitive, and all incoming `RELATION` edges referencing the old ID are dynamically remapped to the new ULID.

## Compliance & Validation Rules
* Parsers MUST reject any primitive payload where the ID does not match the regex prefix corresponding to its primitive class.

# ADR-002: Universal Sensitivity Model, Inheritance, & Redaction Pipeline

* **Status:** Accepted
* **Date:** 5 August 2026
* **Deciders:** Senior Software Architect
* **Technical Domain:** Security, Privacy, & LLM Context Safety

## Context & Problem Statement
The original domain model defined privacy classification (`sensitivity`) only on `ASSERTION`, leaving `ENTITY`, `DIRECTIVE`, `EVENT`, and `RELATION` vulnerable to silent PII leakage into LLM prompts.

## Decision Drivers
* **Leakage Containment**: Prevent private medical, financial, or credentials data from reaching third-party LLM inference APIs.
* **Unrotatable Data Rule**: Personal facts cannot be revoked once disclosed.

## Decision Outcome

### 1. Universal Sensitivity Field
The `sensitivity` attribute is promoted to a **universal required property across ALL 5 Primitives**.
* **Allowed Values:** `public`, `internal`, `restricted`.

### 2. Sensitivity Definitions
* **`public`**: Data safe for open publication or public template sharing.
* **`internal`**: Personal data safe for local AI processing via trusted endpoints, but restricted from public repos.
* **`restricted`**: Highly sensitive data (credentials, financial records, medical details, raw PII) that **MUST NEVER enter an LLM context window**.

### 3. Sensitivity Inheritance Rules
1. **Edge Inheritance:** A `RELATION` edge automatically inherits the **maximum sensitivity** of its `source_id` and `target_id`.
   $$	ext{Sensitivity}(	ext{RELATION}) = \max(	ext{Sensitivity}(	ext{Source}), 	ext{Sensitivity}(	ext{Target}))$$
2. **Entity Scoping Inheritance:** When a `DIRECTIVE`, `ASSERTION`, or `EVENT` is linked to an `ENTITY` with `sensitivity: restricted`, the linked primitive defaults to `sensitivity: restricted` unless explicitly overridden by the human user.

### 4. Sanitization & Redaction Pipeline
* **Zero-Width Character Stripping:** Pre-commit hooks MUST strip all zero-width spaces (`U+200B`), zero-width joiners (`U+200D`), and bidirectional text overrides (`U+202E`) from all string fields across all primitives.
* **Secret Scanning:** All primitive fields are scanned against standard credential regexes (API keys, RSA keys, JWT tokens) prior to indexing.
* **Prompt Exclusion:** The context compilation engine MUST filter out any primitive where `sensitivity == restricted`.

## Compliance & Validation Rules
* Any context builder that emits a primitive with `sensitivity == restricted` into an LLM prompt payload violates security compliance and MUST halt execution immediately.

# ADR-003: Graph Semantics, Directionality, Predicates, & Traversal Bounds

* **Status:** Accepted
* **Date:** 5 August 2026
* **Deciders:** Senior Software Architect
* **Technical Domain:** Knowledge Graph & Multi-Hop Query Engine

## Context & Problem Statement
The domain model specified `RELATION` edges without defining directionality, inverse inference rules, predicate vocabulary governance, or graph recursion limits, creating risks of circular loops and query failure.

## Decision Drivers
* **Multi-Hop Traversal**: Support queries like "Find all projects governed by security constraints."
* **Deterministic Execution**: Prevent stack overflow or infinite loops during graph traversal.

## Decision Outcome

### 1. Directionality
All `RELATION` edges are strictly **directed** (`source_id` $\rightarrow$ `target_id`).
* `source_id`: Origin primitive identifier.
* `target_id`: Target primitive identifier.

### 2. Standardized Core Predicate Enum
Implementations MUST support the following standardized core predicates:

| Predicate | Semantic Meaning | Allowed Source Types | Allowed Target Types |
|---|---|---|---|
| `governs` | Directive applies to target | `DIRECTIVE` | `ENTITY`, `ASSERTION` |
| `owns` | Source owns/maintains target | `ENTITY` | `ENTITY`, `ASSERTION` |
| `depends_on` | Source requires target | `ENTITY`, `ASSERTION` | `ENTITY`, `ASSERTION` |
| `supersedes` | Source replaces target | `ASSERTION`, `DIRECTIVE` | `ASSERTION`, `DIRECTIVE` |
| `supports` | Source provides evidence for target | `ASSERTION`, `EVENT` | `ASSERTION` |
| `located_at` | Source is positioned in target | `ENTITY`, `EVENT` | `ENTITY` (environment) |
| `member_of` | Source belongs to group/org | `ENTITY` | `ENTITY` |

### 3. Predicate Extension Pattern
Custom predicates are permitted if prefixed with `ext_` (e.g., `ext_collaborates_on`). Free-form non-prefixed strings are prohibited.

### 4. Inverse Traversal Rules
Query engines MUST implement inverse relation mapping for core predicates:
* `source` $\xrightarrow{	ext{governs}}$ `target` $\iff$ `target` $\xleftarrow{	ext{governed\_by}}$ `source`
* `source` $\xrightarrow{	ext{depends\_on}}$ `target` $\iff$ `target` $\xleftarrow{	ext{required\_by}}$ `source`
* Custom `ext_` predicates DO NOT receive automatic inverse inference unless an explicit inverse mapping is registered.

### 5. Traversal Bounds & Cycle Handling
* **Maximum Depth Limit:** Recursive CTE queries MUST enforce a hard depth cap of **$	ext{MAX\_DEPTH} = 3$**.
* **Cycle Prevention:** Traversal algorithms MUST maintain a visited node tracking array (`visited_ids`). Re-encountering an ID along an active path immediately terminates that branch.

## Compliance & Validation Rules
* Graph engines MUST reject recursive queries without a depth limit or visited-node tracker.

# ADR-004: Context Activation Policy, Token Budget Overflow, & Compiler Rules

* **Status:** Accepted
* **Date:** 5 August 2026
* **Deciders:** Senior Software Architect
* **Technical Domain:** Context Engineering & Prompt Compilation

## Context & Problem Statement
The original specification capped Tier 0 (Always-On Preamble) at ≤500 tokens but provided no overflow strategy, fallback demotion rules, or deterministic sorting policy when candidates exceed the budget.

## Decision Drivers
* **Prompt Reliability**: Prevent distractor interference and token bloat.
* **Deterministic Builds**: Guarantee that identical PAKB source data produces identical context files across runs.

## Decision Outcome

### 1. Activation Tiers
* **Tier 0 (Always-On Preamble):** Static preambles (`CLAUDE.md`, `.cursorrules`, `AGENTS.md`). Strictly capped at **500 tokens**.
* **Tier 1 (On-Demand MCP):** Served dynamically via local MCP server resource endpoints (`resources/read`, `tools/call`).
* **Tier 2 (Restricted Vault):** Stored locally; redacted from prompts.

### 2. Tier 0 Candidate Eligibility
A primitive is eligible for Tier 0 if and only if:
1. `primitive == ENTITY` AND `type == owner`
2. `primitive == DIRECTIVE` AND (`enforcement == hard` OR `domain == global_style`)
3. `sensitivity != restricted`

### 3. Priority Ranking Order for Tier 0
When candidate primitives are evaluated for Tier 0 inclusion, they MUST be sorted in the following strict order:
1. `DIRECTIVE` (`enforcement == hard` AND `domain == security`)
2. `ENTITY` (`type == owner`)
3. `DIRECTIVE` (`enforcement == hard` AND `domain == code_style/safety`)
4. `DIRECTIVE` (`enforcement == soft` AND `domain == global_style`)
5. Secondary Sort: `last_verified` timestamp (descending / newest first).
6. Tertiary Sort: `primitive_id` (alphabetical ascending for deterministic tie-breaking).

### 4. Overflow & Demotion Mechanics
1. Candidates are added to the preamble in Priority Ranking order until adding the next item would exceed 500 tokens.
2. Any candidate `DIRECTIVE` with `enforcement == soft` that cannot fit within the 500-token cap is **demoted to Tier 1 (On-Demand MCP)**.
3. **Hard Constraint Safeguard:** `DIRECTIVE` items with `enforcement == hard` CANNOT be demoted to Tier 1. If the sum of all `enforcement == hard` directives alone exceeds 500 tokens, the build compiler MUST fail with `PreambleBudgetExceededError`.

## Compliance & Validation Rules
* Compilers MUST verify that generated Tier 0 preambles never exceed 500 tokens.

# ADR-005: Composition Rules, Metadata Restrictions, & Graph Normalization

* **Status:** Accepted
* **Date:** 5 August 2026
* **Deciders:** Senior Software Architect
* **Technical Domain:** Information Architecture & Data Normalization

## Context & Problem Statement
The inclusion of an optional `metadata` dictionary on primitives created a risk where developers would embed sub-entities or hierarchical structures inside JSON blobs rather than creating explicit `RELATION` edges, breaking graph queries.

## Decision Drivers
* **10-Year Durability**: Prevent domain schema drift and unstructured JSON clutter.
* **Graph Queryability**: Ensure all entity relationships remain queryable via SQL / recursive CTEs.

## Decision Outcome

### 1. `metadata` Field Restrictions
The `metadata` dictionary on any primitive is **strictly restricted to ephemeral UI or tool-internal state**:
* **Permitted Metadata Keys:** `editor_cursor_pos`, `ui_collapsed_state`, `import_source_path`, `cli_theme_override`.
* **Prohibited Metadata Keys:** Sub-entities, domain relationships, foreign-key string lists, or factual assertions.

### 2. Mandatory Edge Creation Rules
An explicit `RELATION` edge MUST be created whenever:
1. An `ENTITY` contains sub-workstreams, sub-goals, or sub-tasks (e.g., `source: project_A`, `target: subtask_1`, `predicate: owns`).
2. A `DIRECTIVE` governs a specific `ENTITY` or `ASSERTION` (e.g., `source: directive_security`, `target: repo_B`, `predicate: governs`).
3. An `ASSERTION` supersedes another `ASSERTION` (e.g., `source: new_decision`, `target: old_decision`, `predicate: supersedes`).

### 3. Explicit Prohibited Anti-Patterns
1. **Anti-Pattern A (Embedded Entities):** Placing nested arrays of JSON objects inside `metadata`.
2. **Anti-Pattern B (Custom Scoping Keys):** Adding un-spec'd foreign key string fields (such as `scoped_entity_id`) to `DIRECTIVE` or `ASSERTION`.
3. **Anti-Pattern C (Delimited Id Lists):** Storing comma-separated lists of target IDs inside text fields.

## Compliance & Validation Rules
* Pre-commit schema validators MUST reject primitive payloads where `metadata` contains keys matching foreign primitive prefixes (`ent_`, `dir_`, `ast_`, `evt_`).
